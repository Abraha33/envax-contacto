# ENVAX — Official Construction Plan V1

## 1. Mission

Build ENVAX as a maintainable B2B catalog platform that lets a business discover ENVAX products, organize them into named favorites lists, send a pedido request, and continue with a human advisor. The system must remain simple for customers and maintainable by a very small team.

ENVAX is not an ecommerce store. V1 does not include public checkout, online payment, cart totals, marketplace behavior, or a dependency on live ERP integration.

## 2. Product boundary

### Customer experience

Core flow:

`Landing → business name → business type → catalog → category/brand/family/product → favorites lists → Enviar pedido → solicitud → advisor`

Customer-visible lifecycle:

`Solicitud enviada → En atención → Pedido confirmado → Completado`

### Anonymous mode

The default experience minimizes data collection. ENVAX creates an anonymous account/session after the customer provides business name and business type. The system stores favorites and request history without forcing traditional registration.

Cross-device recovery will use a non-personal recovery credential generated by ENVAX. Portal activation later verifies customer contact data and links the verified customer to the pre-existing anonymous identity.

### Customer portal

Portal activation is optional. Initial portal value is order visibility/status. Do not turn the portal into an ERP, accounting tool, or ecommerce checkout.

### Favorites

Favorites are multiple named lists, for example `Halloween`, `Cumpleaños`, or `Uso diario`. They are not a cart.

### Promotions

Promotions are a later module. An administrator can target a specific customer or a business type. Customers may select one or several promotions and continue to an advisor through WhatsApp/email. Promotions do not create an automatic purchase.

### Seller operations

The system decides seller/advisor assignment. While ERP integration is unresolved, a browser extension can consume seller-selected ERP text and, after validation, update ENVAX from `solicitud` to `pedido`.

## 3. Architecture choice

For V1, optimize for one maintainer, Cloudflare deployment, low operational overhead, and replaceable integrations.

### Chosen stack

- Language: TypeScript end-to-end.
- Package manager: pnpm workspaces.
- Customer/Admin frontend: React + Vite + TypeScript.
- Routing: React Router.
- Server-state: TanStack Query or equivalent small server-state layer.
- Forms/validation: shared schema validation; Zod is the baseline.
- Backend: one modular Cloudflare Worker REST API; Hono is the preferred lightweight router unless Phase 1 proves raw Workers simpler.
- Database: Cloudflare D1 for operational relational data.
- SQL/type layer: Drizzle ORM/schema as baseline; generated SQL migrations committed to Git.
- Assets: Cloudflare R2.
- Async/retry work: Cloudflare Queues, introduced only when needed.
- Abuse protection: Turnstile on abuse-prone public forms/endpoints, server-verified.
- Internal admin protection: Cloudflare Access is preferred for the first internal admin deployment, with application RBAC added where business roles require it.
- Testing: Vitest for unit/integration, Playwright for browser E2E.
- Browser extension: Chromium Manifest V3 first, with a browser-neutral core parser package.

Do not introduce microservices, Kubernetes, a separate message broker, or a second database in V1 unless a measured requirement forces it.

## 4. Build strategy

Build in vertical slices. A phase is complete only when its outcome can be exercised end-to-end.

### Phase 0 — Product/Design/Build readiness

Goal: prevent implementation from guessing product decisions.

Deliverables:
- canonical product docs linked;
- construction plan approved;
- unresolved product fields explicitly marked pending;
- UX visual work runs in parallel;
- source-of-truth rules documented;
- no ERP capability assumed.

Exit: `PRODUCT READY` and `BUILD PLAN READY`.

### Phase 1 — Foundation and Cloudflare skeleton

Goal: create the technical base without changing the current live landing unexpectedly.

Deliverables:
- pnpm workspace;
- `apps/customer`, `apps/admin`, `services/api`, `packages/*`, `tools/catalog-import`, `extensions/seller` skeletons;
- current landing isolated under `apps/landing` only after staging proves identical behavior;
- existing QR Worker preserved;
- local/staging/prod configuration model;
- lint, formatting, typecheck, unit-test and build scripts;
- GitHub Actions CI;
- Cloudflare preview/staging deployment;
- secrets excluded from Git.

Exit gate: clean CI + all deployable shells work independently + landing regression check passes.

### Phase 2 — Catalog data foundation

Goal: serve a real catalog without depending on Wappsi.

Deliverables:
- canonical import format generated from Product Master;
- deterministic import script;
- D1 catalog schema;
- product/category/brand/family/variant read API;
- image/asset metadata model in R2;
- public/private asset access policy configurable;
- search/filter baseline;
- import validation report and rollback strategy.

Exit: same source file imports deterministically; catalog API passes contract tests; no ERP call required.

### Phase 3 — Customer catalog shell

Goal: make the approved visual catalog navigable.

Deliverables:
- landing handoff into customer app;
- catalog home/index;
- category, brand, family, listing, product detail;
- search and filters;
- responsive behavior;
- loading/empty/error/404 states;
- analytics event hooks without coupling UI to analytics provider.

Dependency: visual screens for each implemented section must pass Design Ready first.

Exit: a test user can reach any seeded product from the landing on desktop and mobile.

### Phase 4 — Anonymous identity and named favorites

Goal: remember a customer with minimal friction.

Deliverables:
- anonymous identity creation;
- secure session cookie;
- business name/type persistence;
- anonymous recovery credential generated by ENVAX;
- cross-device restore flow using that credential;
- multiple named favorite lists;
- add/remove/move items;
- rename/delete list;
- favorites survive new sessions and device recovery;
- no IP-based identity.

Exit: favorites persist, restore works, and no personal contact data is required.

### Phase 5 — Pedido request and advisor handoff — Commercial MVP

Goal: convert catalog interest into an actionable commercial request.

Deliverables:
- `Enviar pedido` from a favorites list and from selected products;
- immutable request line snapshots;
- optional note and optional quantity fields where applicable;
- internal `solicitud` record;
- deterministic seller assignment policy;
- customer-visible status mapping;
- WhatsApp click-to-chat handoff and email adapter/fallback;
- confirmation screen/message;
- idempotency preventing duplicate submissions;
- admin/read-only operational view sufficient to see incoming requests.

Exit: real test customer submits once; advisor context is correct; duplicate/retry does not create a second request.

**This is the first commercial MVP. Pilot here before expanding scope.**

### Phase 6 — Seller extension and operational conversion

Goal: eliminate repeated manual re-entry while ERP API remains unresolved.

Deliverables:
- 5–10 real seller-selected ERP text samples collected first;
- deterministic parser fixture suite;
- extension captures only explicit user-selected text;
- exact request matching;
- normalized extraction preview when ambiguous;
- automatic fast path when all required fields validate;
- extension API authenticated and idempotent;
- successful processing creates/links `pedido` and changes the customer-visible state;
- audit trail;
- optional Google Sheet bridge only if operations still need it.

Exit: test request converts to order exactly once from a known ERP sample; ambiguous text never writes silently.

### Phase 7 — Customer portal

Goal: let verified customers recover and view order history/status without losing anonymous data.

Deliverables:
- anonymous → verified customer upgrade;
- email or WhatsApp verification adapter (only enabled when a real provider is configured);
- merge/link rules;
- `Mis pedidos` and order detail/status timeline;
- logout/session management;
- account recovery;
- favorites remain available from the customer app.

Exit: a recovered anonymous user upgrades and sees the same historical request/order relationship.

### Phase 8 — Admin + promotions

Goal: give ENVAX controlled commercial targeting.

Deliverables:
- admin promotion CRUD;
- target one customer or one/more business types;
- activation dates/status;
- recipient materialization/audit;
- customer promotion inbox/landing;
- select one or several promotions;
- handoff selected promotions to WhatsApp/email/advisor;
- opt-out/consent records where required by the selected outbound channel.

Exit: admin targets a test business type; only matching users see/receive the promotion; selected promotions reach the advisor context.

### Phase 9 — Hardening, observability and production pilot

Goal: make the system safe and supportable.

Deliverables:
- accessibility pass;
- browser/device matrix;
- performance budgets;
- security review;
- rate limits/Turnstile where justified;
- backup/restore drill;
- structured logs and request IDs;
- operational metrics and alerts;
- failure/retry tests;
- data-retention policy implementation after policy approval;
- production runbook;
- customer pilot and measured fixes.

Exit: `PRODUCTION READY` only after restore, security, E2E and pilot gates pass.

## 5. Parallel ERP/API track

ERP validation is not a construction phase dependency.

Track:

`documentation review → real credentials/environment → read tests → customer/invoice tests → order write test → reliability/security test → adapter implementation → controlled rollout`

Until that track passes, the core system uses the Product Master/import pipeline and seller extension bridge.

All ERP access is behind an `ErpGateway` interface. No browser frontend or extension receives ERP secrets.

## 6. Milestones

### Milestone A — Catalog usable
Phases 1–4 complete.

Customer can enter, explore, be remembered, and manage named favorites.

### Milestone B — Commercial MVP
Phase 5 complete.

Customer can send a pedido request and reach the advisor with correct context.

### Milestone C — Operational platform
Phases 6–8 complete.

Seller bridge, order visibility, admin and promotions operate end-to-end.

### Milestone D — Production ready
Phase 9 complete.

## 7. Indicative effort for one maintainer

These are planning ranges, not promises:

- Phase 1: 3–5 focused days
- Phase 2: 5–8
- Phase 3: 7–12 after visual approval
- Phase 4: 5–8
- Phase 5: 5–8
- Phase 6: 5–10 after real ERP samples exist
- Phase 7: 5–8
- Phase 8: 7–10
- Phase 9: 5–10

A realistic complete path is roughly 8–14 focused development weeks for one maintainer, with the first commercial MVP materially earlier. AI-assisted development may reduce typing time but does not remove validation, testing, design, security, or pilot work.

## 8. Rules that prevent scope drift

1. Do not block core ENVAX on Wappsi.
2. Do not build checkout/payment/cart totals.
3. Do not build every future portal feature before the commercial MVP.
4. Do not write directly to D1 from browser apps or extension.
5. Do not put secrets or real customer/ERP data in the public repo.
6. Do not implement customer-facing UI before its visual state is approved.
7. Do not add infrastructure products until a phase needs them.
8. Every write endpoint must define authorization, validation, idempotency and audit behavior.
9. Every phase must have automated tests and an exit gate.
10. Preserve independent deployment of landing, customer app, admin, API, extension and QR Worker.

## 9. Definition of done for any feature

A feature is done only when:
- product behavior matches canonical docs;
- UI/state behavior is defined;
- validation and permissions exist;
- database migration is versioned if needed;
- tests cover happy path and failure path;
- logging/observability is sufficient to diagnose it;
- secrets are server-side;
- staging passes;
- rollback is understood;
- documentation is updated.
